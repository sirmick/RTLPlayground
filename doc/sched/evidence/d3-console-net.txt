## What D3 does

1. Control-frame TX buffer (8eb7be5, net.md). ctl_buf[RTL_FRAME_DESC_SIZE
   12 + CTL_FRAME_MAX 256] and ctl_len, in banked frame_tx.c. STP, LACP and
   LLDP build their frames there (compile-time size asserts) and send with
   ctl_output(); tcpip_output() and ctl_output() set tx_buf/tx_len and call
   the static frame_output(). RLDP builds no frames (the chip's engine);
   IGMP replies stay in uip_buf. Common area -237 B.
   Review fix (5840390): at 8eb7be5 CTL_FRAME_MAX was 152 and the asserts
   checked only struct lldp_pkt; LLDP's TLV writes weren't bounded by it.
   With a long hostname and port name a frame ran past ctl_buf into
   ctl_len, tx_buf, tx_len and cmd_parser's vlan_names (the next symbols in
   xdata): every LLDP send erased the VLAN names, and the port description
   went out with ctl_len/tx_buf's bytes in it. Before D3 the frame was built
   in uip_buf, which has room. Now CTL_FRAME_MAX = LLDP_MAX_FRAME 256 (and
   LLDP_MAX_PAYLOAD its frame less the 22 B header); sysname, sysdesc and
   the port description are cut to their arrays (hostname[24],
   machine_name[30], PORT_NAME_SIZE 32), and rtl837x_lldp.c checks at
   compile time that every TLV at its bound fits: 192 B of payload with
   today's 20-character version string, 234 B allowed. xdata +104 B.
2. con / cli (689e548, console.md). cmd_editor.c edits its own
   con_line[CMD_BUF_SIZE]; Enter sets con_line_ready (an empty line too),
   and while it is set the editor reads nothing (U2). con posts EV_LINE and
   waits on EV_CON_RX only (the echo busy-waits in write_char, as all
   output does). The cli task (tasks.def: fixed, once): CLI_IDLE takes the
   console line first, then a queued web command; CLI_RUN copies con_line
   into cmd_buffer and tokenizes + parses, or runs httpd_webcmd_run();
   CLI_PROMPT prints the prompt then clears con_line_ready (type-ahead
   echoes after the prompt), or, for the web, posts EV_CMD_DONE.
   cmd_service() and the cmd_available bit are gone.
3. The web command (689e548, f142690; net.md item 2). The /cmd body is
   queued in config_buf (webcmd_pending, TSTATE_WEBCMD); the rx task posts
   EV_WEBCMD after rx_service() (httpd can't include sched.h: the host tests
   have no sched_gen.h); cli runs it, the reply captured in outbuf, sets
   webcmd_done; the connection's next uip_poll sends it (send_outbuf(),
   factored out of do_send).
   Review fix (9462bdf): data arriving on the /cmd's connection while it is
   queued (a trailing CRLF in a segment of its own, a pipelined request)
   took the generic branch: request_header_take() copied it over the
   command in config_buf and left TSTATE_WEBCMD, so the clobbered text ran,
   the reply was never sent and a timeout didn't cancel it. In
   TSTATE_WEBCMD new data is now dropped, as today's code drops data that
   arrives while its reply is sent (TSTATE_TX).

## The web command buffer: config_buf, 0 bytes (QA d3-webcmd-buf)

The book (memory.md, console.md) planned a separate ~128 B buffer. As
built it is config_buf, and that is safe:
- uIP has one TCP connection (uip/uip-conf.h UIP_CONF_MAX_CONNECTIONS 1;
  cmd_parser.c's health tcp dump #errors otherwise; in rtlsim a second
  concurrent connection is reset, "tcp: found no unused connections").
  While the /cmd waits in TSTATE_WEBCMD no other request can arrive, so
  nothing else writes config_buf or outbuf.
- No command touches config_buf: only httpd.c uses it (the config save is
  POST /config, a request of its own).
- The one window: the /cmd's connection ends (reset, abort, timeout) after
  the queue and before cli runs; the next request then lands in config_buf.
  At 50ccedb the pending command still ran then (from config_buf, whatever
  it held by then). f142690: closing or aborting a TSTATE_WEBCMD connection
  clears webcmd_pending and webcmd_done; CLI_IDLE no longer clears
  webcmd_pending, CLI_RUN re-checks and clears it right before running, and
  CLI_PROMPT posts EV_CMD_DONE only if webcmd_done. Both flags are set in
  httpd_init (xdata isn't zeroed at startup). A /cmd queued again in
  between is the one that runs: it is what config_buf holds, and its
  connection is the one waiting.
- httpd.c #errors if UIP_CONNS != 1: with more connections the command and
  its reply need buffers of their own (body up to CONFIG_UPLOAD_BUF 4480 B,
  today's /cmd limit; the reply up to TCP_OUTBUF_SIZE 2500 B).
A version with its own buffers (webcmd_buf 4480 B + webrep_buf 2500 B,
xdata +6983 B) was built and dropped once the one-connection fact was
found (the QA thread has the exchange).

## The web command around config uploads, and cancelled (tools/webcmd_abort.py)

  python3 tools/webcmd_abort.py <-boot image> --board ~/src/ovs-rtlpg/boards/<board>.json
  W1: POST /config, /cmd "ip\nversion", POST /config, /cmd: each reply is
      the commands' output, each upload in flash (0x7f000).
  W2: /cmd "hostname aborted" and a client RST injected in the same instant
      (both in the NIC ring; rx takes up to RX_BUDGET 4 frames a step, so the

      "hostname cfgbody ..." on a new connection: hostname unchanged, the
      console says only "tcp: got reset, aborting connection.", upload in
      flash.
  W3: /cmd "hostname tail3\nip", then a CRLF in a segment of its own in the

      the hostname is set, the reply is ip's output, no parse error.
