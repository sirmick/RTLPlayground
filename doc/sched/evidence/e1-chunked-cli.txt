## What the steps cost, and why (QA e1-tx-ring, decision 21)

tools/cli_steps.py IMAGE --web: each command between `health clear` and
`health tasks`, console and web /cmd; the CLI tour of the old-vs-new
scenarios plus port N, stp status, health tasks, history; ports 2, 3 linked,
STP on, VLANs 10 and 20. Longest cli step, f621897 (M2):
    version 5.1 ms, port 5.9, stp 9.7, stp status 23.6, storm 28, vlan show
    30, stat 40, lacp show 42, health tasks 71, history 186 ms
The same image with con_putc dropping bytes instead of waiting (an
experiment, not committed), CLI_RUN read from xdata:
    version 1.3, port 1.2, stp 1.4, stp status 2.6, vlan show 2.6, storm 2.8,
    lacp show 3.0, stat 3.7, l2 0.6 (few MACs); history 8.9, health tasks 9.2
So the 5 ms limit was broken by the 128 B TX ring at 115200 baud (87 us a
byte): anything printing more than ~185 B. Decision 21: the ring is 2 KiB,
and only what grows with a table, or whose work passes 5 ms, is a job.

## What E1 does

- con_ring: TX 2048 B, 16-bit head and tail. con_putc writes the head and
  reads the tail in one ES-off section a byte (the start of an idle
  transmitter in it too); con_tx_room reads the tail with ES off; the ISR
  alone writes the tail otherwise. isr_serial pushes 8 (was 7): sched.mk's
  ISR_SERIAL_PUSHES, checked by isr_frame.py. con_putc no longer kicks the
  watchdog. Host tests (test_sched): 2047 free, EV_CON_TX below 100, the
  drain, 7 x 1500 B through the ring in order (the indexes wrap 5 times),
  full, and a byte into a full ring with ES off polling TI.
- cli jobs (cmd_parser.c cli_job, cli_job_more, cmd_finish): l2 (a table
  search a step), stat and lacp show (a port or a LAG a step: their work
  plus a web reply's capture passed 5 ms), history (a line, 64 bytes looked
  at at most; its own line saved after the dump, as before), health tasks
  (a slot, a state, the totals), stp off's BPDU entries (stp_fdb_line: 256
  VLAN reads a step, an entry written counts 16; 4094 reads were 33 ms in
  one step). The boot's stat and the config at boot run a job to its end.
- tasks.c: CLI_MORE runs a job's line a step after EV_CON_TX (room for a
  line); a command starts with 1 KiB free (CLI_ROOM). A web /cmd: CLI_RUN
  begins it (httpd_webcmd_begin), CLI_NEXT runs a command a step
  (exec_line: execute_commands split, the same stop rules), its job in
  CLI_MORE, CLI_PROMPT completes the reply (httpd_webcmd_end). The capture
  is on only during cli's steps (WEBCMD_CAPTURE_ON/OFF), so other tasks'
  prints between steps aren't in the reply. A connection that ends drops the
  command at cli's next step (webcmd_busy).
