1. Strings vs code
-----------------------------------------------------------------------------

- Each module's area sizes come from its .rel.
- Its __code data comes from the .asm: .ascii, .db and .dw under data
  labels. String literals are SDCC's ___str_N; anything else is "other

- code = area - data.
- Banked totals leave out the pinned assembly modules: crc16 (bank 1) and

-----------------------------------------------------------------------------
2. A fourth 48 KiB code bank
-----------------------------------------------------------------------------

How the banks sit today:
- imagebuilder packs bank n at 0x4000 + (n-1)*0xc000. Bank 1 is at 0x04000,
  bank 2 at 0x10000, bank 3 at 0x1c000, and the code ends at 0x28000, which
  is HTML_START.
- A bank 4 would occupy 0x28000-0x34000.

What it would need:
- Linker: -Wl-bBANK4=0x44000 in the Makefile's link line, which today lists
  only HOME and BANK1-3.
- tools/place_banks.py: BANKS = 3 is a constant. It would have to come from
  the layout.
- imagebuilder: already generic; it derives nbanks from the file size.
  bank_occupancy.sh already lists BANK4.
- check_layout.py --code: the code must end below the new HTML_START.
- The CPU and the sim: crtbank takes PSBANK & 0x1f, so up to 31 banks.
  rtlsim maps (psbank-1)*0xc000 generically. Neither limits it.
- The loader:
  - alias_find() scans banks 1..0x3f, and load_slot() handles only the home
    bank; neither depends on the bank count.
  - But LDR_DATA (0x3a000), LDR_SLOT (0x3c000) and LDR_APP_A_END (=
    LDR_DATA) are fixed, in both layouts. A compact image larger than
    0x3a000 moves them.
  - So that is a new loader layout (3), and a two-step update for every
    installed unit: first the loader, then the application. An old loader
    would install only up to 0x3a000 and read its slot at 0x3c000, which
    would then be web UI.
- The POE-2G040210GSM puts its PSE image at 0x34000, the end of bank 4. A
  fifth bank would collide with it; bank 4 alone doesn't.

The SWGT024 (512 KiB): it does not fit.
- The compact budget on 0x80000: two images (running and staged), the
  loader's data (0x6000), the loader stage (0x4000), the update progress
  sector (0x1000) and the config (0x1000). So 2*I + 0xc000 <= 0x80000, and
  I <= 0x3a000: today's IMAGE_SIZE exactly.
- With four banks the code ends at 0x34000. That leaves 24 KiB for the web
  UI and the 4 KiB default config.
- The web UI uses 66,279 B of its 69,632 B region today.
  - LANGS=en shrinks it to about 39.8 KB gzipped (app.js minified:
    165,864 -> 90,427 B).
  - It still needs about 44 KB with the config: about 20 KB too much.
- Even if the loader stage and the progress sector were shared with the
  upload area (+0x5000), I could only reach about 0x3c800. The web UI and
  config would get about 34 KiB, still short of the 44 KB needed.

The 8x (2 MiB): it fits, two ways.
- (a) The standard layout with LOADER=1 (loader layout 1), which already
  exists.
  - The code may run to LDR_DATA (0x3a000), so four banks (ending at
    0x34000) fit; a fifth does not.
  - The web UI moves to 0x40000, and uploads are staged at 0x80000 (2 MiB
    has room).
  - Cost: the deployed 8x units run compact. Going compact -> standard is a
    layout migration that has no tool yet; test_migrate covers only
    standard -> compact.
- (b) A compact layout for flashes of 1 MiB or more: HTML_START 0x34000,
  IMAGE_SIZE 0x46000, and the loader data and staging moved up.
  - Cost: the loader-layout change above.
- Today's compact 8x map, for reference:
    0x00000  loader
    0x04000  banks
    0x28000  web UI
    0x39000  default config
    0x3a000  loader data
    0x40000  upload stage
    0x7a000  loader stage
    0x7e000  progress
    0x7f000  config
    0x80000  MDATA (to 0x8c000)
  1.45 MiB above that is unused.
- Either way, a fourth bank helps only the 8x. On the SWGT024 every feature
  must still fit three banks, so the extra bank's code must be optional for
  512 KiB boards.

3. SDCC options per file
-----------------------------------------------------------------------------

Method:
- Each module compiled with the build's own flags plus one switch, and the
  BANKED area compared.
- The base compile reproduces the build's .rel byte for byte.
- All 44 banked C modules were done (sched_gen_names is generated, so left
  out), on both boards.

Results, in BANKED bytes:

  variant                          8x total  saved    SWGT024 saved
  base                             144654    0        0
  --opt-code-size                  =         0        0
  --opt-code-speed                 =         0        0
  --max-allocs-per-node 25000      =         0        0
  --max-allocs-per-node 100000     =         0        0
  --max-allocs-per-node 1          =         0        0
  --noinduction                    144249    405      404
  --noinvariant                    144003    651      651
  --noinduction --noinvariant      143632    1022     1021
  --noloopreverse                  144660    -6       -6
  --nogcse                         149679    -5025    -5024
  --nolabelopt                     145540    -886     -882

  (= means the output is byte-identical to base.)

- --opt-code-size and --max-allocs-per-node have no effect at all on mcs51
  with this SDCC. max-allocs tunes the newer register allocator, which mcs51
  doesn't use.
- --noinduction and --noinvariant help some files and grow others.
  - noinduction grows httpd +166 and uip_arp +34.
  - noinvariant grows httpd +5.
  - So the best switch per file saves 1286 B on the 8x: bank 1 196, bank 2
    540, bank 3 550. On the SWGT024 it saves 1285 B.

  Per-file picks:
    rtl837x_leds_dump  both            -323
    cmd_parser         noinduction     -245
    httpd/page_impl    both            -178
    rtl837x_port       noinvariant     -140
    dns                both            -126
    ntp_cli            noinduction      -81
    sfp                noinvariant      -71
    uip/uiplib         noinduction      -25
    rtl837x_lacp       noinvariant      -23
    rtl837x_storm      noinvariant      -22
    rtl837x_rldp       noinvariant      -14
    others                         <= -11 each

- RAM effect, all modules together:
  - noinduction: DSEG 74->62, OSEG 41->31; XSEG +18 B.
  - both switches: DSEG 74->61, OSEG 41->28.
  So less internal RAM, and a little more xdata.
- The cost: loops run slower in those files, because induction variables and
  invariants are recomputed in the loop. They are CLI and print paths, plus
  page_impl's JSON loops.

4. Commands that could be build-optional on compact boards
-----------------------------------------------------------------------------

A command can be optional only if the web UI doesn't use it. app.js sends
these through /cmd, so they must stay:
  syslog, stp, ntp, lacp, bw, lag, mirror, led, storm, sfp, session, passwd,
  mtu, loop, lldp, laghash, l2, isolate, ingress, igmp, eee, dns.

-----------------------------------------------------------------------------
Options ranked by bytes gained vs risk
-----------------------------------------------------------------------------

1. CLI-only diagnostic commands optional on compact boards (a make flag, as
   HEALTH is).
   - Gain: about 8 KB: bank 3 2.8 KB, bank 1 1.6 KB, bank 2 3.6 KB.
   - Risk: low. Plain #ifdefs, and the web UI doesn't use these commands.
   - Cost: no register, PHY, SerDes, LED or cable diagnostics in those
     builds.
2. Usage and syntax text cut to a short "Error: syntax" plus the command
   name.
   - Gain: about 1.5-2 KB of the 2.3 KB, nearly all in bank 2.
   - Risk: low, in the code. Users get less help, and oldnew needs expect
     lines for the changed replies.
3. Per-file optimizer switches (--noinduction, --noinvariant, the best for
   each file).
   - Gain: about 1.3 KB, spread 196 / 540 / 550 B.
   - It also uses 13 B less DSEG and 13 B less OSEG.
   - Risk: low to medium. Loops in those files get slower, so oldnew and the
     long-step checks need a re-run. There is less optimizer exposure, if
     anything.
4. Merging duplicate literals.
   - Gain: at most 644 B, realistically 0.2-0.3 KB.
   - Risk: low, but the effort is medium: a shared literal must be in HOME
     or within one bank.
5. A fourth bank: 8x only (standard layout with LOADER=1, or a new loader
   layout). It does not fit the SWGT024.
   - Gain: 48 KB on the 8x only.
   - Risk: high. A layout migration of deployed units, a loader update,
     build tooling, and any code placed there has to be optional on 512 KiB
     boards.
6. --opt-code-size and --max-allocs-per-node.
   - Gain: 0 B. No effect on mcs51 with this toolchain.
