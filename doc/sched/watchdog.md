# 11. Software watchdog and crash record

Code: `crash.h`, `crash.c` (resident), the ISRs in `rtlplayground.c`,
`crash_boot()` and `state.sys.reset`'s getter in `sched_health.c`, `build_id.h`
(generated by `sched.mk`).

## Watchdog

There is no hardware watchdog (chapter 2). The software one counts down in
the tick ISR:

```c
/* isr_timer2, after the tick: SWDT_ISR(ISR_T2_PUSHES), crash.h */
if (swdt_on && !--swdt_cnt) {
	crash_cause = CRASH_SWDT;
	crash_pc_sp = SP - pushes;	/* where the interrupted PC is */
	__asm__("ljmp _crash_die");	/* fills the record, resets; never returns */
}
```

- A jump, not a call: any call in an ISR makes SDCC save every register on
  every entry. `pushes` is the ISR prologue's push count, 8 in both
  `isr_timer2` and `isr_serial` (`ISR_T2_PUSHES`, `ISR_SERIAL_PUSHES` in
  `sched.mk`); `tools/isr_frame.py` reads the real count from the `.asm` at
  every build and fails it if they differ.
- `swdt_kick()` at each pass's start sets `swdt_cnt = 1000`: **5 s**
  (`SWDT_TICKS`). It must be far above the step limit (50 ms, decision 25) and the erase
  (40 ms); the watchdog catches hangs, not slow steps. It counts from the
  pass's kick, not the step's start, so a step that hangs fires it 4995-5000
  ms after it began (b5-neg-tests.txt).
- **Off until the scheduler runs.** `sched_run()` sets `swdt_on`; the boot
  runs without it. A chip reset before the switch init hangs the chip
  (chapter 2), so a watchdog reset during the boot would hang the board
  instead of resetting it.
- **No kick in `con_putc()`** (E1). Until E1 a wait for room in the TX ring
  kicked it, because an unchunked `l2` could print for longer than 5 s in
  one step. Now the dumps that grow with a table are cli jobs, the ring is
  2 KiB, and a command starts with 1 KiB free, so a step waits on the UART
  only if it prints more than the free ring. To reach 5 s it would have to
  print ~57 KB in one go; the largest unchunked outputs are a few hundred
  bytes (`vlan show` 465 B, e1-chunked-cli.txt). A loop that prints for
  ever is caught at 5 s like any other hang.
- It can't catch a hang with interrupts off, or inside an ISR at the tick's
  priority. Nothing on this chip can.

Proven: in the sim, schedtest's `ST_NEG=hang` resets after 5 s with the
record naming `slow/SL_HANG` (b5-neg-tests.txt); on the 8x, the same, PC
inside `sl_hang`, twice (silicon.md, C).

## Crash record

At a fixed xdata address, **0xbfe0** (the last 32 bytes of the 48 KiB),
outside every XSEG: the app's ends at 0x5109 (fb-build.txt), the loader's
at 0x4f6a. The C start-up clears only XSEG, so the record survives a chip
reset through the loader (C, DB, EB on the 8x); a power cut clears it.
**32 bytes:**

| Offset | Size | Field |
|---|---|---|
| 0 | 2 | magic `0x5c4d` |
| 2 | 1 | cause: 1 software watchdog, 2 `^R ^R`, 3 `reset` command (4 reserved: below) |
| 3 | 1 | resets recorded since power-on, before this one |
| 4 | 2 | tick at the reset |
| 6 | 1 | running slot (`sched_cur`) |
| 7 | 1 | its state |
| 8 | 2 | tick when that step started |
| 10 | 1 | SP of the interrupted code |
| 11 | 1 | PSBANK |
| 12 | 2 | PC of the interrupted code (from the stack in the ISR); 0 if not from an ISR |
| 14 | 8 | the last 8 states run (a ring) |
| 22 | 1 | ring index |
| 23 | 1 | spare |
| 24 | 4 | the image that wrote it: `CRASH_IMAGE_LO`, `_HI` |
| 28 | 2 | spare |
| 30 | 2 | 16-bit sum of bytes 0-29 |

- `CRASH_NOTE(slot, state)`, in the loop before each dispatch, keeps the
  slot, state, start tick and ring current: a few xdata writes.
- `crash_die()` (resident) fills in the rest and the sum, and resets. The
  tick ISR and the `^R ^R` path jump to it (`CRASH_FROM_ISR`); every other
  reset is `reset_chip(cause)`, which drains the console and calls
  `crash_reset(cause)`: `do sys.reset` (cause `cmd` on the console, `web`
  over the web, as POST /reset), the button (`button`, either hold),
  `do sys.factory_reset` (`factory`), an update (`update`).
- **The image's identity** (E0). `crash_die()` stores 32 bits of a SHA-1
  over the version (`v0.1.0-<hash>[-dirty]`), the build date and the build
  directory (machine, layout, schedtest and its variants), which `sched.mk`
  writes per build into `build_id.h`. `crash_boot()` takes a record only
  if its magic, sum and identity hold; another image's valid record is
  dropped unread (magic cleared). Found on the 8x in DB: a schedtest record
  survived a web update and was decoded with the firmware's names
  (silicon.md). `tools/crash_foreign.py` checks it in the sim, `test_sched`
  on the host.
- **An update's record** (P5-1). Cause 4, `update`, is the one record
  `crash_boot()` takes from another image: the reset that applies an
  upload (and the install or loader conversion at boot) boots an image
  that isn't the one that wrote it. It keeps the cause, step time and bank,
  and drops the slot, state, ring and PC (another image's names), which
  read as `-`. (E3 dropped the cause; the object model wants every reset's
  cause.)
- "Resets since power-on" counts recorded resets: the boot that consumes a
  valid record carries its count + 1 into the next record (`crash_prior`).
- **Boot:** `crash_boot()`, before the prompt: a valid record is copied
  into `crash_last` and its magic cleared. A power-on finds garbage: the
  magic or the sum fails. `get state.sys.reset` shows it (P5-1; the boot's
  `Last reset:` line and `health tasks`' went with it):
  `state.sys.reset.cause ctrl_r`, `.slot con`, `.state CON_EDIT`,
  `.step_ms 0`, `.pc 18236`, `.bank 2`, `.states` (the last 8 states, oldest
  first); cause `power` with no record.
- A `^R ^R` typed during the boot, before the main loop runs, resets
  without a record once the boot is done (`serial_reset_pending`), as
  before.
- The loader doesn't use the address (its XSEG ends at 0x4f6a). schedtest's
  `ST_CRASH=8000` puts the record at 0x8000 for a bench comparison.
